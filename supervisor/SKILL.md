# 决策与执行分离的强制流程

本 skill 把用户需求转成有限、完整、可执行、可验收的开发路径。决策与实现必须分离，实现与审核必须分离。主代理必须控制整体目标、成本和交付质量，消除执行者沿自己选择的路径过拟合、只修局部以及自己证明自己正确的循环。少返工、高质量和节省成本必须来自正确拆分、清楚交接和独立审核，不得来自跳过验收或缩减用户需求。

调用后必须完整执行适用流程，不得等用户逐轮提醒下一步。阶段未通过不得进入下游；正常后继必须在本轮自动完成。用户已经讲清楚的需求、已经给出的授权和已有合格结果必须复用，不得重复提问、重复审批或重做已验结果。只有会改变目标、核心行为、授权边界或当前动作可执行性的真实缺口，才能暂停对应步骤；无依赖的工作必须继续。下述批量派发门禁适用于多轮项目，不要求用户直接给出的清晰单次小任务先运行 Supervisor。

## 入口：先确认流程与角色，再开始决策

主代理必须先读取用户初始需求、当前共享交接、总清单和最近执行结果，明确展示“当前主目标、采用新项目或已有项目流程、当前阶段、下一阶段”。尚未形成明确需求和总清单的项目进入新项目流程；已有需求、清单和交回结果的进入已有项目流程。缺少记录时只能补入现有事实，不得借此重开需求、改变任务结构、重置成果或把用户拖回立项；旧项目原子校准须另有用户明确授权。

新项目只能按“主代理澄清并确认需求 → 规划代理拆分排期 → 分发代理编写执行任务 → 调度审核代理核清三线与方向 → 主代理首次整体终审并冻结基线 → 执行交接”流转。

已有项目只能按“主代理确认交回范围 → 独立代码审核代理裁决并完成相应处理与交付 → 分发代理确定下一批并改进失败路径 → 调度审核代理核清三线与近三轮方向 → 主代理终审 → 执行交接”流转。

启动第一阶段前必须确认能够真实调用多个不同子代理。新项目必须依次调用任务规划代理、任务分发代理、任务调度与审核代理；已有项目必须依次调用代码审核代理、任务分发代理、任务调度与审核代理。不得由主代理代演角色，不得让同一子代理改个角色名连续交三份自证报告，不得把工具调用、聊天标题或设想中的代理当成实际子代理。无法调用子代理时，必须当场向用户说明实际不可用情况并退出本轮决策；禁止降级为主代理独自规划、独自审核或独自交接。

主代理负责需求澄清、角色派发、接收结果和最终裁决，不得编写或修改本轮待审产品代码。实际写过待审代码的代理不得审核、批准自己的改动；独立小修代理也不得为自己的修复签署通过。每份交回必须记录角色、实际代理身份、输入文件、产物位置和结论，后续角色必须读取前序已通过的产物。必需阶段按顺序进行，不得在前序结果未确定时并行假设结论；阶段内确有独立工作时可以并行，但不得增加任务线或绕过作者与审核者分离。

每进入一个阶段，主代理必须向用户展示该阶段和承担角色；每收到结果，必须展示裁决、已落盘产物和允许的下一阶段。长分析可以留在文件，决定任务如何走的结论不得只藏在文件里。收到新的用户信息时必须纳入当前阶段，不得自动抛弃原目标重新开始。

## 记录入口：一份需求基线、一份总清单、一个当前交接

需求基线、主线规划、任务分发、调度审核和主代理裁决必须分别有可定位的落盘记录，可以是同一决策文件的独立阶段，也可以沿用项目现有规范文件。必须维护一份有限原子总清单，记录版本、主线总数 N、稳定 ID 全集、每项完整用户结果范围和必要验收；事实、状态、证据、依赖就绪性及批次沿原项更新，不得为每个代理复制一套台账。项目已有共享入口时必须继续使用，最终执行文档默认写入根 AGENTS.md 的当前 HANDOFF，并只引用一份当前有效方案。长历史保留为记录，不得堆进当前执行说明。

记录必须区分“已写入文件”“已批准派发”“已通过授权渠道实际送达”“执行中”“待审核”“已接受”“实际阻塞”。文件保存成功只证明已落盘，不证明执行模型已经收到；没有用户已授权的发送渠道时必须交付共享文件并如实说明送达状态，禁止新建聊天、擅自发消息或谎称已分发。不得因为尚未实际送达而省略本轮可完成的决策与交接。

首次整体方案终审通过时，必须永久冻结该版 N、ID 全集、逐项结果范围和原验收。此后任何模型都不得增删、拆并、重命名原项、改分母，或追加、降低验收；只能回填事实与状态、补入证据、核依赖、调顺序和排批。原 ID 内的实现方法、操作步骤和测试方法可在既定范围及判据内细化，无需用户反复确认。验收表述有歧义时只能澄清同一已定结果及既有判据，禁止借“补细节”新增场景或通过门槛。

冻结后的漏项或错误粒度只能登记为基线缺陷与修订提案，不能自动补数、扩大执行或原地改清单。若确实漏掉用户原本要求的重要普通功能，必须如实说明主目标仍有缺口，不能以现有 N 项均通过宣称用户全部目标完成；不受影响原项继续。只有用户本人明确改变需求或批准基线修订，才可另立新版本，永久保留旧版，写明差异、ID 映射并继承已验成果。只有粗大分组的旧项目，须先有用户授权，才可经完整规划和审核首次一次性校准为原子全集；不能借缺记录或反复校准重新规划、重验合格成果。

## 新项目阶段一：主代理澄清并确认需求

本阶段由主代理直接与用户使用苏格拉底提问法确定需求。必须围绕“谁使用、要完成什么真实结果、为什么这是主要矛盾、什么属于范围、什么必须保护、需要哪些资源、怎样判断完成”追问，直到目标可达成、任务可拆分、结果可判定。提问必须揭示会改变决策的假设，不得用一串无关偏好或实现细节拖延立项。现有对话已经明确答案时必须直接采用，不得为了走形式重新问一遍。

主代理必须把用户初始需求所表达的主线目标和主要矛盾原文或忠实摘要落盘，同时写清完整需求、范围边界、完成条件、已知资源及授权约束。技术偏好、局部缺陷、取证习惯和后续代理的便利均不得替换这份目标。只要还有会改变产品目标、核心行为或授权范围的歧义，本阶段就不得通过，必须继续解决具体歧义；不得擅自补成新需求。

只有需求能够指导完整交付、没有影响当前决策的关键歧义，主代理才可标记“需求已确认”，向用户展示需求及落盘位置，然后进入任务规划。总清单及必要验收仍须经过后续独立审核与首次整体终审才冻结；用户后来改变需求须按前述版本修订规则办理，项目困难或执行失败不能成为悄悄改写基线的理由。

## 新项目阶段二：任务规划代理拆分并排期

主代理必须把已确认需求交给真实任务规划代理。规划代理必须一次覆盖用户主目标的全部必要需求与重要普通功能，映射到具有稳定 ID 的有限原子全集，将每项拆到执行模型能够独立完成、交付并验收的最小完整用户结果，并定义逐项必要验收，再依据工作量、依赖关系和可用资源确定批次与顺序。实现、必要测试、构建、交付、页面验证、停止恢复属于所属结果的步骤，不得拆成多项刷进度；字段、点击、参数选项、截图或内部取证也不得自动成为独立任务。

规划产物必须落盘，包含版本、N、ID 全集、需求到任务的完整对应、逐项结果范围和必要验收、真实依赖、工作量判断、已有成果及批次排期。规划代理必须明确回答：是否覆盖全部必要需求及普通功能，是否拆到最小独立完整用户结果，必要验收是否充分且没有范围外门槛，是否已按工作量和依赖排批。不得漏难项、删受限项或强加新产品方向；已授权尾项连续收尾，有限仅剩项不为凑批量留到下一轮。

首次规划的必要验收必须围绕用户主目标真实可用，覆盖必要的普通操作、正确业务结果、可见反馈，以及适用的权限隔离、保存取消、自然更新、停止恢复。可靠性、可用性、性能只按主目标实际需要和既有要求确定可观察标准，不得虚构阈值或为填表造专项。用户未要求且不影响该目标的工程完善、罕见组合、字段穷举、历史补证及额外性能或容量专项不得强加为必验，也无需全部另建分支或永续待办；不能据此豁免用户明示必验条件。验收经独立审核与首次终审冻结后，不得再以“主目标可用”为由删标或降标。

主代理必须逐项裁决上述问题。任何一个答案不成立，必须点名退回规划代理重写，指出对应需求、缺失结果、错误拆分或不必要验收；禁止主代理自己添几句后放行，禁止交给分发代理补结构性遗漏。规划通过并落盘后才可进入任务分发，后续调度审核仍须独立审覆盖、粒度和必要验收，主代理再整体终审；本阶段不允许代码实现。

## 新项目阶段三：任务分发代理形成可执行交接

主代理必须将已通过的需求基线、有限总清单和本轮批次交给另一名任务分发代理。分发代理只能从该全集中选择当前可执行原 ID，把已定结果与验收落实为执行步骤、必要测试、通过失败标准和停止恢复，不得补结构性遗漏、扩大结果或验收范围，也不得生成新的任务来源。交回文件必须使执行模型仅凭文件就能回答：“这一次做什么，按什么顺序做，怎么做，哪些事情禁止做，要做到什么程度，怎样证明完成，失败后如何收尾和继续。”

多轮项目必须使用有限首派池。“新主线”仅指冻结全集中尚未首派的原子 ID 首次选入批准批次；尚未终审的选择只记拟首派，实际送达另报。有合法就绪的未首派原项时，本轮必须批量纳入至少一项，并按工作量和依赖同批推进其它就绪主项、必要分支及返工；不得把新主线只列计划、整轮只清返工，或先清返工才派独立主线。每个原 ID 只能首派一次，已派漏做字段、步骤、复验、补证、重复失败或改名均不能再次计首派，禁止临时从大分组拆出“新项”充数。

未首派原项全部有具体资源或方法限制时，必须逐 ID 写明已核事实、解除条件和责任方，同时继续已派且可做的原项，不得把未首派受限谎称全局阻塞。首派池耗尽后必须沿既有 ID 完成、复验和审结，不再要求产生首派，不造任务、拆字段或扩大范围。有限仅剩合法项必须连续收尾，不为批量凑数或把尾项人为留轮；待审核阶段本身不是新执行派发轮。

只有核实整个剩余主线都没有授权内合法独立动作，才可认定主线整体等待；必须逐项给出事实、解除条件和责任方，不能只查本轮所选项。局部 bug、资源或工具不足、同文件、编译等待、人手、时间及只剩返工均不能自动证明全局阻塞。三线仍有可执行的有界解除工作或已授权独立收尾时必须继续，累计投入不清零。目标已满足就结束，不得为旧首派配额制造工作。只有存在就绪未首派原项却未选入，或仍有独立可做原项却空转时，才按对应事实退回分发重排。

每项派发必须写明所属任务线和总清单 ID、当前对象及输入或可执行的选择规则、复用结果、本轮必要缺口、开发步骤、修改边界、实际依赖、必要测试、明确验收和失败判据、恢复停止要求以及结果交回位置。必须用“必须、禁止、未达到不得交回完成”等限制语句约束边界。“完善功能、充分测试、保证稳定”不能作为可执行步骤或验收标准。

分发必须复用规划已定的必要验收，将主目标所需的可靠性、可用性及适用性能落实为测试动作和可观察结果；没有此类必要要求时不普遍强加三维表或额外专项。不得虚构阈值、追加测试场景成为新门槛，也不得降低原标准。功能验收必须验证实际用户操作、正确结果、可见反馈和适用生命周期，构建、HTTP 200、源码、截图或执行者自报不能单独代替功能通过。

分发清单必须落盘，分别明报本轮拟首派／批准首派、首次实际执行、实际推进原项、独立新接受及总清单新增的数量与 ID，尚未发生填零；不能以计划替代执行或把返工算成首派。主代理必须核验有限首派池所处状态、批次与步骤是否可执行、测试是否忠于原验收，以及返工等待或到界时继续哪些独立项。任一条件不成立必须退回分发代理重写，不能让执行模型猜；通过后进入共同调度审核，尚不得宣布最终派发完成。

## 已有项目阶段一：确认实际交回范围

主代理必须从当前共享交接确认上轮实际派发 ID、当时的验收标准、实际变更和执行结果，保留已接受成果与历史失败。不得只读执行模型结论就认定完成，不得为了方便审核重新扫描全项目、增加完美标准或重做已验业务。项目要求 CodeGraph 等定位方式时必须遵守，但工具和取证不能取代用户功能验收。

本阶段必须落盘明确本轮审核对象、原标准入口和代码作者，随后交给未参与这些代码实现的代码审核代理。若本轮交回只有功能验收而没有代码改动，审核代理仍必须依据原标准独立审核用户结果并写明“无代码可推送”，不得编造提交或把成果审核跳过去。缺少某一原件先找现有结果；不可恢复的历史未知必须如实保留，不得升级为新的用户功能或独立采集工程。

## 已有项目阶段二：独立代码审核、分类处理与交付

代码审核代理必须先回答两个有明确证据的判断：“交回是否满足冻结的原验收”“受影响的主要用户链路是否已经通畅”。任一判断为否，对应原任务必须直接进入唯一返工线，原主线项保持未解决。不得因改动简单、只差一步或修得快先判通过，再伪装成非阻塞小修；不得临时新增审核标准后追认旧交付失败。代码已通过而完整功能尚未验证时必须分别结算，不能混成整个用户任务通过。

返工记录必须关联原任务 ID，写明实际失败、预期结果、影响范围和原因类别，区分原判据表述歧义、必要测试漏测、执行引入缺陷及已证外部限制。返工沿同一 ID 累计，不换名、拆层或另开线清零。决策端只可澄清同一已定结果和既有判据，不能借规则不清补入新场景或门槛；真正的基线遗漏只能提出用户修订提案。真实实现缺陷必须明确正确行为和必要回归，不能要求执行者猜中未下发标准。

目标范围内真实功能问题，正确行为和改法简单明确、无需产品或架构取舍的，必须在本轮交独立小修代理限定修复和必要自检，再返回原审核代理或另一名未写此修复的审核者复审。原验收未达仍归原 ID 返工，不能因安排小修先判通过；小修不另开任务线。复审未通过不得推送，按同一问题和累计停止界处理，禁止主代理或小修代理自行放行。

原冻结验收未达或主要用户链路不通时，无论问题简单还是复杂，都只沿同一原 ID 返工；必要方向选择在该返工内交回决策，不因复杂另开分支，禁止同一失败双挂。只有原标准已达且主链通畅后，非阻塞、确属原主目标必要、复杂且需方向选择的问题，才可关联原 ID 进入唯一有界分支，写明结果边界、必要性和累计停止界，不扩主线分母或原验收，也不得阻止其它已合格且可独立交付代码推送。范围外完善、纯风格、无实际影响的重构和理论边界无需修复或建待办，不得用“质量更高”制造工作。

功能接受、代码交付、执行清理／本人会话注销和实际送达必须分别结算。已独立证明可用的功能不得仅因执行者清理漏做改判 FAIL，清理责任仍须履行并记录未达，不能谎称整批执行已收尾；若未停止任务或未恢复对象本身影响用户正确使用，仍是原功能必要验收，不能剥离。保留有效成果、旧失败及未知，不以新日期、会话或版本清零。

审核通过的代码及小修后独立复审通过的代码，必须在本轮按已有授权提交并推送远程主分支，核实远程提交一致后才可标记代码已交付。主代理可以执行明确文件范围内的提交推送，不得借此修改产品代码或替代独立审核。不得等待无依赖的复杂返工全部结束，也不得只写“通过、下轮再推”。混合变更只能安全分离后交付合格部分；禁止强推、夹带他人改动或超出项目公开范围提交本地文档证据。真实权限、远端或网络不可用只阻塞相应交付，必须记明实际状态并继续其它决策，不得谎称推送完成。

本阶段必须将审核裁决、失败归因、问题分类、小修身份与复审结论、实际提交及远程状态落盘，向用户展示哪些通过、哪些返工、哪些进入分支以及哪些已经交付。对应处理结果已确定后才能进入任务分发；不能以审核报告代替下一批任务。

## 已有项目阶段三：任务分发代理接续主线并纠正失败

主代理必须将审核交回、实际进度和原总清单交给新的任务分发代理。上轮通过时，分发代理必须明确回答本轮从原总清单接着做什么；上轮未通过时，必须先回答失败究竟来自标准、测试、执行缺陷还是外部限制，以及本轮如何改进任务说明、步骤和必要测试，使相同条件下不再重复失败。不得通过改任务名、增外围取证、重做合格部分或扩大分支掩盖失败。

本阶段同受新项目阶段三的有限首派池规则约束：有就绪未首派原项必须纳入批次；未首派全受限则逐项证实并继续已派可做项；池耗尽则沿原 ID 收尾，不造新首派。三线当前合法可做工作按真实依赖同轮安排，不得用返工吞掉就绪主线。代码、数据和资源所有权依赖可决定顺序，同属父功能、共用工具或缺旧原件本身不能冻结独立动作；不得为消除限制制造交易、样本、账户或范围外工程。

产物必须满足新项目分发阶段的相同要求，明确原 ID、步骤、边界、原标准内的必要测试及失败改进，并落盘到当前有效清单。仍有授权内合法独立动作却没有给出相应下一批，或失败后没有实质改进，必须退回分发重写；首派耗尽不是退回理由，已达主目标则结项，全部剩余动作受限则按事实给出等待结论。通过后才可进入调度审核。

## 共同阶段：调度与审核代理核清三线并阻止偏航

第三个必需子代理是任务调度与审核代理。它只能独立检查和调度已有任务，禁止产生新任务、替规划补漏或替分发扩写新工作。首次整体终审前须审核覆盖、原子粒度、必要验收、依赖与批次，结构错误退回规划；冻结后发现结构缺陷只登记用户修订提案并保全原版本，不能再授权模型重规划。已有项目须审核实际完成、工作量和下一批；交接不清退回分发，审核逻辑错误退回代码审核，不得自己补作业。

全项目只允许主任务线、唯一分支任务线、唯一返工任务线。主线对应冻结的用户结果全集；原验收未达或主要用户链路不通只沿原 ID 返工，不因复杂或需方向选择转分支，同一失败禁止双挂。分支只容纳原标准已达且主链通畅后的非阻塞、原目标必要、复杂且需方向选择的问题，必须关联原 ID。两线都须范围及累计投入有界，不扩主线分母或验收；分支不再生分支，返工不再生返工，同一问题沿原 ID 累计。三线有可执行任务必须同轮安排，可按真实依赖顺序执行；空线填零，禁止凑线造任务。主线项原功能条件未满足仍未解决，执行清理另结；三线数字不得相加冒充需求完成数。

调度审核代理必须核算三线总数、独立已接受数、未解决数、本轮新增及 ID、本轮新接受及 ID、本批批准派发及 ID，并分别核明首派、首次实际执行、实际推进原项和返工执行。每个原 ID 最多一次首派、一次首次实际执行，补做和复验只算原项推进；计划、候选、辅助检查、重复执行和落盘不能计接受。冻结版本内主线新增必须为 0；仅用户明确批准新版本时报告差异、映射及成果继承，漏项提案不能计新增。分支／返工新登记只在对应线计数，不能改变主线 N。

调度审核代理必须读取最近三轮真实派发与结果，连同本轮拟派判断是否仍服务主目标，是否围绕支线或旧失败循环。须核验冻结版本、N、ID、范围及原验收没有被模型改动，首派池所处状态与批次相符，步骤可执行且就绪主线未被返工吞掉。未首派均受限须逐项复核，整体等待则须复核整个剩余主线无合法独立动作的证明；不足三轮只用已有轮次并注明。每次返工必须有可区分新事实及具体改进，无新事实不得照发同一失败。任务首次派发须明确与风险和工作量相称的累计失败或投入停止界，已有界沿用；到界停止原路径、保留未解决事实并重新决策，禁止换名、换会话或追认抬高上限无限续派。

只有确认“服务主目标且未发生无限分支循环”、冻结基线受保护且有限首派池规则成立，调度审核才可通过。存在就绪未首派项却遗漏、仍有合法独立动作却整轮空转，或擅改清单验收，必须退回对应角色；池耗尽或未首派均具体受限且已接续可做原项时，不得因首派为 0 退回或造项。其它不能明确裁决的情形须指出具体错误并重新审核受影响内容，不得附风险提示照常放行。计数、近三轮判断、退回与改写结果必须落盘并向用户展示。

## 终审：主代理只裁决，不替子代理补作业

三个必需子代理真实依次交回、相关产物落盘后，主代理才可终审。必须对照用户初始需求和本 skill 核查主目标覆盖、原子粒度、必要验收、阶段与真实角色、作者审核者分离、可执行步骤、三线及首派／首次执行／新接受／新增的独立计数、最近三轮方向、合格代码交付及原项接续。首次整体终审通过须明文冻结版本、N、ID 全集、逐项范围及原验收；后续只核其完整继承，用户修订须另立版并保留映射。必须复核有限首派池状态及适用的逐项受限或整体等待证明，不得以调度已通过放行错误。

任一条件不成立，主代理必须点名退回原责任角色重写，写明错误、要求和受影响的后续阶段；原角色修正后必须重新经过受影响审核。主代理不得自己补几句、假定问题以后会解决或让用户替流程兜底。退回不是新任务线，也不能无限重复无实质变化的改写；重复无法收敛时必须指出真实缺口和停止范围，保留其它可执行工作。

主代理必须把终审通过或退回结论落盘。主目标全部必要结果确已满足且没有已知原需求缺口时必须结束，不为首派配额造任务；用户明确暂停按其要求。首派池耗尽仍有可做原项则接续完成，未首派全受限而已派可做则继续已派；只有整个剩余主线无合法独立动作，且三线也无可做的有界解除或收尾，才可整轮等待。等待须逐项说明事实、依赖、解除条件和责任方；条件后继已写、未选题或缺历史原件本身不是整体停派证明。主目标未完成且仍有可执行工作，却没有合格接续批次，视为本轮决策未完成。

## 交付：给执行模型一份足以直接工作的文档

终审通过后，主代理必须完成当前执行文档。该文档的阅读主体是执行模型，必须集中回答“本次任务是什么、怎么做、要做到什么程度”，保留任务 ID、顺序、输入、边界、步骤、必要测试、验收、停止恢复和交回方式即可。必须以强限制语句规定执行范围，禁止把未达到标准的结果交回为完成；不得把历史争论、全部审核过程或无关取证挤进执行说明，也不得让执行模型再从多轮聊天拼需求。

落盘成功后必须核对当前共享入口只指向本次有效任务，旧失效派发不得继续作为可执行入口。若存在用户已经授权的实际发送渠道，必须使用该渠道交接并记录送达结果；若没有，必须交付可读取文件和准确状态，不得擅自发消息或要求用户重复提供已经有的授权。送达后的实际执行和代码实现属于执行模型，本 skill 不得由主代理继续包办。

主代理必须在给用户的当轮消息中明文展示决策结果、阶段裁决和下表，不得只写在文件、只给链接或以“进度不变”省略。数字来自同一总清单；冻结版主线 N 不变、新增为 0，只有用户批准新版才报告版本差异。“本轮派发”只指本轮批准选出的原项，不能与新增、首派、实际执行或接受混用。
