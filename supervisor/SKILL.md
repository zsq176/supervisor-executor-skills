# 决策与执行分离的强制流程

本 skill 把用户需求转成有限、完整、可执行、可验收的开发路径。决策与实现必须分离，实现与审核必须分离。主代理必须控制整体目标、成本和交付质量，消除执行者沿自己选择的路径过拟合、只修局部以及自己证明自己正确的循环。少返工、高质量和节省成本必须来自正确拆分、清楚交接和独立审核，不得来自跳过验收或缩减用户需求。

调用后必须完整执行适用流程，不得等用户逐轮提醒下一步。阶段未通过不得进入下游；正常后继必须在本轮自动完成。用户已经讲清楚的需求、已经给出的授权和已有合格结果必须复用，不得重复提问、重复审批或重做已验结果。只有会改变目标、核心行为、授权边界或当前动作可执行性的真实缺口，才能暂停对应步骤；无依赖的工作必须继续。

## 入口：先确认流程与角色，再开始决策

主代理必须先读取用户初始需求、当前共享交接、总清单和最近执行结果，明确展示“当前主目标、采用新项目或已有项目流程、当前阶段、下一阶段”。尚未形成明确需求和总清单的项目进入新项目流程；已经有需求、任务清单和交回结果的项目进入已有项目流程。已有项目缺少规范记录时必须用已有事实补齐，不得借此重开需求、重置已完成任务或把用户拖回立项。

新项目只能按“主代理澄清并冻结需求 → 规划代理拆分排期 → 分发代理编写执行任务 → 调度审核代理核清三线与方向 → 主代理终审 → 执行交接”流转。

已有项目只能按“主代理确认交回范围 → 独立代码审核代理裁决并完成相应处理与交付 → 分发代理确定下一批并改进失败路径 → 调度审核代理核清三线与近三轮方向 → 主代理终审 → 执行交接”流转。

启动第一阶段前必须确认能够真实调用多个不同子代理。新项目必须依次调用任务规划代理、任务分发代理、任务调度与审核代理；已有项目必须依次调用代码审核代理、任务分发代理、任务调度与审核代理。不得由主代理代演角色，不得让同一子代理改个角色名连续交三份自证报告，不得把工具调用、聊天标题或设想中的代理当成实际子代理。无法调用子代理时，必须当场向用户说明实际不可用情况并退出本轮决策；禁止降级为主代理独自规划、独自审核或独自交接。

主代理负责需求澄清、角色派发、接收结果和最终裁决，不得编写或修改本轮待审产品代码。实际写过待审代码的代理不得审核、批准自己的改动；独立小修代理也不得为自己的修复签署通过。每份交回必须记录角色、实际代理身份、输入文件、产物位置和结论，后续角色必须读取前序已通过的产物。必需阶段按顺序进行，不得在前序结果未确定时并行假设结论；阶段内确有独立工作时可以并行，但不得增加任务线或绕过作者与审核者分离。

每进入一个阶段，主代理必须向用户展示该阶段和承担角色；每收到结果，必须展示裁决、已落盘产物和允许的下一阶段。长分析可以留在文件，决定任务如何走的结论不得只藏在文件里。收到新的用户信息时必须纳入当前阶段，不得自动抛弃原目标重新开始。

## 记录入口：一份需求基线、一份总清单、一个当前交接

需求基线、主线规划、任务分发、调度审核和主代理裁决必须分别有可定位的落盘记录，可以是同一决策文件的独立阶段，也可以沿用项目现有规范文件。必须使用稳定任务 ID 和统一状态；不得为每个代理复制一套互相矛盾的台账。项目已有共享入口时必须继续使用，最终执行文档默认写入根 AGENTS.md 的当前 HANDOFF，并只引用一份当前有效方案。长历史保留为记录，不得堆进当前执行说明。

记录必须区分“已写入文件”“已批准派发”“已通过授权渠道实际送达”“执行中”“待审核”“已接受”“实际阻塞”。文件保存成功只证明已落盘，不证明执行模型已经收到；没有用户已授权的发送渠道时必须交付共享文件并如实说明送达状态，禁止新建聊天、擅自发消息或谎称已分发。不得因为尚未实际送达而省略本轮可完成的决策与交接。

## 新项目阶段一：主代理澄清并冻结需求

本阶段由主代理直接与用户使用苏格拉底提问法确定需求。必须围绕“谁使用、要完成什么真实结果、为什么这是主要矛盾、什么属于范围、什么必须保护、需要哪些资源、怎样判断完成”追问，直到目标可达成、任务可拆分、结果可判定。提问必须揭示会改变决策的假设，不得用一串无关偏好或实现细节拖延立项。现有对话已经明确答案时必须直接采用，不得为了走形式重新问一遍。

主代理必须把用户初始需求所表达的主线目标和主要矛盾原文或忠实摘要落盘，同时写清完整需求、范围边界、完成条件、已知资源及授权约束。技术偏好、局部缺陷、取证习惯和后续代理的便利均不得替换这份目标。只要还有会改变产品目标、核心行为或授权范围的歧义，本阶段就不得通过，必须继续解决具体歧义；不得擅自补成新需求。

只有需求能够指导完整交付、没有影响当前决策的关键歧义，主代理才可标记“需求基线已冻结”，向用户展示冻结结果及落盘位置，然后进入任务规划。用户后来改变需求时必须明示基线如何变化；项目困难或执行失败不能成为悄悄改写基线的理由。

## 新项目阶段二：任务规划代理拆分并排期

主代理必须把冻结需求交给真实任务规划代理。规划代理必须把全部需求映射到具有稳定 ID 的主线总清单，将每项任务拆到执行模型能够一次独立完成、交付并验收的最小完整结果，再依据工作量、依赖关系和可用资源确定下发批次与顺序。实现、必要测试、构建、交付、页面验证、停止恢复属于同一结果的执行步骤，不得拆成多项刷进度；一个功能内的字段、截图或内部取证也不得自动变成独立任务。

规划产物必须落盘，包含需求到任务的完整对应、每项任务的结果与完成条件、真实依赖、工作量判断、当前状态和批次排期。规划代理必须明确回答：任务是否覆盖所有需求或功能，是否已经拆到最小可执行完整单元，是否已经按工作量和依赖分好下发批次。不得漏掉难项、删掉受限项，也不得顺手增加平台工程、特殊工况、证据采集工程或用户未要求的产品方向。

主代理必须逐项裁决上述三个问题。任何一个答案不成立，必须点名退回规划代理重写，并指出对应需求、缺失结果或错误拆分；禁止主代理自己添几句后放行，禁止交给分发代理补结构性遗漏。规划通过并落盘后才可进入任务分发；本阶段不允许代码实现。

## 新项目阶段三：任务分发代理形成可执行交接

主代理必须将已通过的需求基线、总清单和本轮批次交给另一名任务分发代理。分发代理只能从总清单中选取当前可执行任务，不得重定目标、扩展范围或生成新的任务来源。交回文件必须使执行模型仅凭文件就能回答：“这一次做什么，按什么顺序做，怎么做，哪些事情禁止做，要做到什么程度，怎样证明完成，失败后如何收尾和继续。”

每项派发必须写明所属任务线和总清单 ID、当前对象及输入或可执行的选择规则、复用结果、本轮必要缺口、开发步骤、修改边界、实际依赖、必要测试、明确验收和失败判据、恢复停止要求以及结果交回位置。必须用“必须、禁止、未达到不得交回完成”等限制语句约束边界。“完善功能、充分测试、保证稳定”不能作为可执行步骤或验收标准。

可靠性、可用性和性能必须分别有与任务匹配的处理结论。适用维度必须给出可执行测试和可观察的通过标准，覆盖实际需要的正常结果、错误反馈、状态延续或恢复，以及已有响应时间、数据规模或资源要求。已有标准直接复用；不适用必须说明原因。不得虚构性能阈值，不得为凑三类指标增加正式长稳、故障平台或原范围之外的工程。功能验收必须验证实际用户操作、正确结果、可见反馈和必要收尾，构建、HTTP 200、源码、截图或执行者自报不能单独代替功能通过。

分发清单必须落盘。主代理必须检查任务是否确实下发为可执行说明、交接是否完整、开发步骤与验收是否明确、可靠可用性能要求是否合理。任一条件不成立，必须退回分发代理重写；不得把含糊处留给执行模型猜。通过后进入共同的调度审核阶段，尚不得宣布最终派发完成。

## 已有项目阶段一：确认实际交回范围

主代理必须从当前共享交接确认上轮实际派发 ID、当时的验收标准、实际变更和执行结果，保留已接受成果与历史失败。不得只读执行模型结论就认定完成，不得为了方便审核重新扫描全项目、增加完美标准或重做已验业务。项目要求 CodeGraph 等定位方式时必须遵守，但工具和取证不能取代用户功能验收。

本阶段必须落盘明确本轮审核对象、原标准入口和代码作者，随后交给未参与这些代码实现的代码审核代理。若本轮交回只有功能验收而没有代码改动，审核代理仍必须依据原标准独立审核用户结果并写明“无代码可推送”，不得编造提交或把成果审核跳过去。缺少某一原件先找现有结果；不可恢复的历史未知必须如实保留，不得升级为新的用户功能或独立采集工程。

## 已有项目阶段二：独立代码审核、分类处理与交付

代码审核代理必须先回答两个有明确证据的判断：“交回是否满足原先下发的验收标准”“受影响的主要用户链路是否已经通畅”。任一判断为否，对应原任务必须直接进入唯一返工线，原主线项保持未解决。不得因为改动简单、只差一步或修起来很快而先判通过，再伪装成非阻塞小修；不得临时新增审核标准后追认旧交付失败。代码已通过而完整功能尚未验证时必须分别结算，不能混成整个用户任务通过。

返工记录必须关联原任务 ID，写明实际失败、预期结果、影响范围和原因类别，明确区分验收规则未写清、必要测试漏测、执行过程引入缺陷、已证实的外部限制。返工沿同一 ID 累计，不得换名、拆层或另开返工线清零。规则不清由决策端补成可判定条件，执行者不得被要求猜中未下发的标准；真实实现缺陷必须明确正确行为和必要回归。

只有原验收已经满足、主要链路已经通畅，审核代理才可处理余下非阻塞问题。正确结果明确、无需产品或架构取舍的小问题必须交给独立小修代理在本轮修复；小修代理只负责限定改动和必要自检，修后必须返回原审核代理或另一名未写此修复的审核代理复审。复审未通过则不得推送该修复，必须按真实失败回到同一问题处理，不能由主代理或小修代理自行放行。

非阻塞但需要方向选择、具有独立工作量的大问题，只有证明其推进原主需求后才可进入唯一分支线，并写明关联需求、结果边界和为何需要该工作。它不得阻止已经合格且可独立交付的原改动推送。纯风格偏好、无实际影响的重构和理论上无限的边界不得制造分支、返工或阻止通过；不得用“质量更高”替代实质理由。

审核通过的代码及小修后独立复审通过的代码，必须在本轮按已有授权提交并推送远程主分支，核实远程提交一致后才可标记代码已交付。主代理可以执行明确文件范围内的提交推送，不得借此修改产品代码或替代独立审核。不得等待无依赖的复杂返工全部结束，也不得只写“通过、下轮再推”。混合变更只能安全分离后交付合格部分；禁止强推、夹带他人改动或超出项目公开范围提交本地文档证据。真实权限、远端或网络不可用只阻塞相应交付，必须记明实际状态并继续其它决策，不得谎称推送完成。

本阶段必须将审核裁决、失败归因、问题分类、小修身份与复审结论、实际提交及远程状态落盘，向用户展示哪些通过、哪些返工、哪些进入分支以及哪些已经交付。对应处理结果已确定后才能进入任务分发；不能以审核报告代替下一批任务。

## 已有项目阶段三：任务分发代理接续主线并纠正失败

主代理必须将审核交回、实际进度和原总清单交给新的任务分发代理。上轮通过时，分发代理必须明确回答本轮从原总清单接着做什么；上轮未通过时，必须先回答失败究竟来自标准、测试、执行缺陷还是外部限制，以及本轮如何改进任务说明、步骤和必要测试，使相同条件下不再重复失败。不得通过改任务名、增外围取证、重做合格部分或扩大分支掩盖失败。

分发代理必须同时安排三条任务线中当前可执行的工作，主线仍有可执行余项时不得只派分支和返工。真实代码、数据、资源所有权依赖可以决定顺序；同属父功能、共用工具或缺旧原件本身不得冻结独立动作。外部限制只能暂停实际依赖它的具体动作，不能认定全项目不可用，也不得为消除阻塞制造交易、样本、账户或范围外工程。

产物必须满足新项目任务分发阶段的相同要求，明确任务明细、开发步骤、强边界、可靠可用性能测试和验收标准，并落盘到当前有效分发清单。若没有给出原清单中的下一批 ID，或没有说明失败后的实质改进，本阶段不得通过。主代理必须退回分发代理重写；通过后才可进入调度审核。

## 共同阶段：调度与审核代理核清三线并阻止偏航

第三个必需子代理是任务调度与审核代理。它只能检查和调度已经存在的任务，禁止产生新任务、替规划代理补漏或替分发代理扩写新工作。新项目由它检查规划覆盖、拆分粒度、依赖与批次；已有项目由它检查实际完成、任务变化、工作量和下一批。发现覆盖或拆分错误必须退回规划，发现交接不清必须退回分发，发现审核逻辑错误必须退回代码审核，不得自己造任务修补。

全项目只允许主任务线、唯一分支任务线、唯一返工任务线。主线必须对应用户初始需求总清单；分支只容纳服务同一目标的必要方向性工作；返工只容纳原验收未通过的工作。分支不得再生分支，返工不得再生返工，同一问题必须沿原 ID 累计。三线有可执行任务就必须同轮安排推进，允许因真实依赖顺序执行；空线必须填零，禁止为凑三线造任务。主线项在关联返工关闭并满足原条件前仍未解决，三线数字不得相加冒充需求完成数。

调度审核代理必须核算每条线总任务数、已解决数、未解决数、本轮新增任务数及 ID、本轮新解决数及 ID、本轮派发数及 ID。总清单新增与从旧清单选择下一批必须分开。写计划、提交候选、辅助检查、重复执行和落盘文件不能计入已解决。主线目标只能因用户需求变化而改变；发现原规划漏项必须如实记为基线补正，说明对应原需求和加入前后总数，不能伪装为新产品方向，也不能删难项美化进度。

调度审核代理必须读取最近三轮真实派发与结果，再连同本轮拟下发任务判断：任务量是否膨胀或超出主目标合理需要，新工作是否实质推进主线，最近三轮及即将下发的一轮是否已偏离初始目标、围绕支线或旧失败无限循环。不足三轮必须只用已有轮次并注明，不得编造历史。每次返工必须有可区分的新事实和具体改进；重复同一失败而无新事实时禁止照发。任务首次下发必须明确与风险和工作量相称的累计失败或投入停止界，已有界直接沿用；达到后必须停止原路径、保留未解决事实并重新决策，禁止靠换名、换会话或追认抬高上限无限续派。

只有确认“服务主目标且未发生无限分支循环”，调度审核才可通过。无法给出这个明确结论时，必须列出具体偏离任务及违反的需求或流程，退回对应角色修改，再重新审核受影响内容；不得附一段风险提示后照常放行。进度核算、近三轮与下一轮判断、退回及改写结果必须落盘，并向用户展示裁决。

## 终审：主代理只裁决，不替子代理补作业

三个必需子代理已经真实依次交回、相关产物已经落盘后，主代理才可终审。主代理必须对照用户初始需求和本 skill 检查：主目标是否完整保留，阶段与角色是否真实完成，作者和审核者是否分离，任务是否覆盖完整结果，步骤与验收是否明确，三线数量是否一致，最近三轮与下一轮是否仍推进主线，合格代码是否实际交付，以及下一批是否已从原总清单接上。

任一条件不成立，主代理必须点名退回原责任角色重写，写明错误、要求和受影响的后续阶段；原角色修正后必须重新经过受影响审核。主代理不得自己补几句、假定问题以后会解决或让用户替流程兜底。退回不是新任务线，也不能无限重复无实质变化的改写；重复无法收敛时必须指出真实缺口和停止范围，保留其它可执行工作。

主代理必须把终审通过或退回结论落盘。只有主目标已完成、用户明确暂停，或者三线全部剩余动作都存在授权内无法解决的实际阻塞时，才允许不接下一批。全部阻塞必须逐任务说明真实依赖、已核实事实、解除条件和责任方；“条件后继已写”“还没想好怎么做”“缺历史原件”不得作为整体停派理由。主目标未完成且仍有可执行工作时，审核结束却没有下一批具体 ID，视为本轮决策未完成。

## 交付：给执行模型一份足以直接工作的文档

终审通过后，主代理必须完成当前执行文档。该文档的阅读主体是执行模型，必须集中回答“本次任务是什么、怎么做、要做到什么程度”，保留任务 ID、顺序、输入、边界、步骤、必要测试、验收、停止恢复和交回方式即可。必须以强限制语句规定执行范围，禁止把未达到标准的结果交回为完成；不得把历史争论、全部审核过程或无关取证挤进执行说明，也不得让执行模型再从多轮聊天拼需求。

落盘成功后必须核对当前共享入口只指向本次有效任务，旧失效派发不得继续作为可执行入口。若存在用户已经授权的实际发送渠道，必须使用该渠道交接并记录送达结果；若没有，必须交付可读取文件和准确状态，不得擅自发消息或要求用户重复提供已经有的授权。送达后的实际执行和代码实现属于执行模型，本 skill 不得由主代理继续包办。
